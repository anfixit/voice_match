# Протокол сбора голосовых записей

## Назначение

Этот документ задаёт минимальный воспроизводимый процесс сбора
целевого датасета для `voice_match`. Он нужен для калибровки и
тестирования speaker verification backend в условиях, близких к
реальному применению.

Протокол не превращает эксперимент в судебную экспертизу. Согласие
участников, законность обработки биометрических данных и правила
хранения должны быть определены до начала записи.

## Согласие и псевдонимизация

До записи участник должен получить понятное описание:

- цели сбора;
- состава сохраняемых данных;
- срока хранения;
- лиц, имеющих доступ;
- порядка отзыва согласия и удаления записей;
- допустимых исследовательских сценариев.

В manifest используются только псевдонимные идентификаторы вида
`spk-001`. ФИО, телефон, email и другие прямые идентификаторы в CSV,
именах файлов и Git не помещаются. Таблица соответствия человека и
`speaker_id`, если она необходима, хранится отдельно от аудио и
manifest.

Аудиозаписи, manifest и таблица соответствия не коммитятся в
репозиторий.

## Минимальная схема записи

Для каждого диктора рекомендуется собрать минимум три независимые
сессии. Между сессиями меняется хотя бы время записи, а для проверки
устойчивости можно отдельно менять устройство или канал.

Одна сессия:

- 5 или более речевых фрагментов;
- каждый фрагмент содержит не менее 10 секунд полезной речи;
- без музыки и чужих голосов;
- без шумоподавления и изменения темпа после записи;
- исходный файл сохраняется до любых преобразований.

Минимальный набор условий для первого целевого эксперимента:

1. тихая комната и основной микрофон;
2. другое время или помещение на том же устройстве;
3. целевой канал, например Telegram, телефон или диктофон.

Смешивать разные каналы в один безымянный класс нельзя. Условие
фиксируется в поле `condition`, например `clean`, `telegram` или
`telephone`.

## Формат аудио

Предпочтительный исходный формат:

- WAV или FLAC;
- один речевой канал;
- частота дискретизации не ниже 16 кГц;
- без клиппинга и искусственного усиления;
- без нарезки одного исходного файла на записи, попадающие в разные
  dataset split.

Приложение само приводит вход к mono PCM 16 кГц для текущего ECAPA
baseline. Хранить только преобразованную копию нежелательно: это
лишает возможности повторить эксперимент с другим backend.

## Структура каталогов

Пример локального каталога вне Git:

```text
dataset/
├── recordings.csv
└── audio/
    ├── spk-001/
    │   ├── s01/
    │   │   ├── u01.wav
    │   │   └── u02.wav
    │   └── s02/
    │       └── u01.wav
    └── spk-002/
        └── s01/
            └── u01.wav
```

Пути в manifest должны быть относительными POSIX-путями. Абсолютные
пути, `..`, `~` и обратные слеши отклоняются.

## Recording manifest

Обязательные столбцы:

| Столбец | Назначение |
| --- | --- |
| `recording_id` | Уникальный ID записи |
| `speaker_id` | Псевдонимный ID диктора |
| `session_id` | ID независимой сессии |
| `path` | Относительный путь к аудио |
| `split` | `train`, `calibration` или `test` |

Необязательный столбец `condition` хранит категорию канала или
условия записи.

Пример:

```csv
recording_id,speaker_id,session_id,path,split,condition
spk-001-s01-u01,spk-001,s01,audio/spk-001/s01/u01.wav,calibration,clean
spk-001-s02-u01,spk-001,s02,audio/spk-001/s02/u01.wav,calibration,telegram
spk-002-s01-u01,spk-002,s01,audio/spk-002/s01/u01.wav,calibration,clean
```

Все идентификаторы и `condition` используют переносимый ASCII-набор:
буквы, цифры, точку, подчёркивание и дефис.

## Разделение данных

Один диктор может находиться только в одном split. Валидатор
останавливает обработку, если один `speaker_id` встречается в
`train` и `test` либо в другой комбинации split.

Рекомендуемое назначение:

- `train`: обучение backend, fusion или normalizer;
- `calibration`: обучение преобразования score и выбор operating
  point;
- `test`: однократная итоговая оценка после фиксации алгоритма.

Записи одной исходной сессии нельзя копировать между split под
другими именами. Дубликаты создают скрытую утечку даже при разных
`recording_id`.

## Генерация trial plan

Команда создаёт пары без system score:

```bash
uv run python -m voice_match.evaluation.generate_trials \
  dataset/recordings.csv \
  --output dataset/calibration_trials.csv \
  --split calibration \
  --nontarget-ratio 5 \
  --seed 2026
```

Target trials строятся только между разными сессиями одного диктора.
Пары внутри одной сессии исключаются, чтобы оценка не опиралась на
одинаковый фон и канал одной записи.

Nontarget trials строятся между разными дикторами. При большом числе
возможных пар используется детерминированная выборка с заданным
`seed`. По умолчанию создаётся до пяти nontarget trials на один
target trial.

Выходной CSV содержит:

```csv
enrollment_id,test_id,label,condition
spk-001-s01-u01,spk-001-s02-u01,target,clean+telegram
spk-001-s01-u01,spk-002-s01-u01,nontarget,clean
```

Этот файл ещё не является входом benchmark evaluator: сначала для
каждой пары должен быть рассчитан score и добавлен столбец `score`.
Один и тот же зафиксированный trial plan используется при сравнении
разных моделей.

## Контроль перед benchmark

Перед расчётом метрик нужно зафиксировать:

- версию кода и commit SHA;
- модель и контрольную сумму её весов;
- manifest и trial plan;
- параметры VAD и сегментации;
- алгоритм агрегации score;
- seed генератора;
- описание каждого `condition`;
- список исключённых записей с причиной исключения.

Ручное удаление неудобных ошибок после просмотра test-результата
делает итоговую оценку недостоверной. Правила исключения фиксируются
до запуска на test split.
